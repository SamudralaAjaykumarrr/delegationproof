[`CONTRIBUTING.md`](../CONTRIBUTING.md) — never hand-typed or
extrapolated from an earlier run.

## 6. Fail-closed evidence

**Malformed input never becomes ALLOW.** Two representative fixtures
under `testdata/malformed/` (every fixture in that directory is walked
and asserted by `TestMalformedModelExitCode2` in
`cmd/delegationproof/main_test.go`, and re-walked at the shipped-binary
level by `scripts/verify.sh` step 6):

```sh
$ delegationproof verify testdata/malformed/unknown-approver.json
validation failed: 1 error(s)
[unknown_approver] nonexistent: approval approver "nonexistent" is not a known node id
```

exit `2`.

```sh
$ delegationproof verify testdata/malformed/delegation-depth-exceeds-max.json
validation failed: 1 error(s)
[resource_limit_exceeded] max_delegation_depth: principal "admin" capability billing:refund@billing-service max_delegation_depth 1000000 exceeds max_delegation_depth (64)
```

exit `2`.

**Semantic DENY (exit 1) vs. invalid-input failure (exit 2), stated
explicitly:** exit `1` (§4 above) means the tool parsed a structurally
valid model and correctly found a real invariant violation — the tool
*worked*. Exit `2` (this section) means the tool could not even
establish that the input was a legitimate model to reason about. A
`resource_limit_exceeded` structural error and an
`approval_lifecycle_unproven` *finding* are easy to conflate but are
not the same thing: the former is exit `2` (this section), the latter
is exit `1` (§8 below) — a bounded-search truncation is still a
*semantic* finding ("could not be proven safe"), never a parse failure.

**Resource-limit exhaustion never becomes ALLOW** and **incomplete
lifecycle exploration never becomes ALLOW** are proven white-box, not
via a shell demonstration — see §7 and §8.

## 8. Temporal approval evidence

`examples/billing-approval-lifecycle.json`'s DENY output (§4 above)
already shows `approval_lifecycle_unsafe` fired for `void-unsafe` while
`refund-safe` — governed by a lifecycle that never leaves `"approved"`
— passes silently, demonstrating the safe case is not simply "any
lifecycle present."

The fail-closed truncation case is not shell-demonstrable (it requires
a lowered `limits.MaxExplorationStatesPerLifecycle`, a white-box-only
condition) — cited instead:

- `TestFailClosedTruncationYieldsUnproven`
  (`internal/verify/verify_v6_test.go`): under bound values `1`, `2`,
  `3`, a truncated exploration always produces at least one finding —
  never a clean pass.
- `TestSafeRecordShortCircuitsBeforeUnproven`
  (`internal/verify/verify_v6_test.go`): when one of two standing
  approval records is genuinely safe and the other is truncated, the
  safe record short-circuits the check outright — zero findings, proof
  that "unproven" is only ever reached when no safe record exists, not
  a case where a truncated record incorrectly poisons an otherwise-safe
  operation.

## 9. Performance characterization

No formal benchmark is included in this evidence report, deliberately.
The project's actual, externally-verifiable performance claim is
algorithmic — `O(nodes + edges + operations)`, no backtracking, no
graph search, independently-linear per-record lifecycle exploration
(`docs/architecture.md` §"Complexity") — a structural guarantee provable
by reading the algorithm and the resource-bound tests above, not
something a wall-clock number would add confidence to. A `go
test -bench` number would be noisy across shared CI runners, carries no
security-relevant signal (an attacker cannot exploit "10% slower than
last commit," but can exploit unbounded allocation — already covered by
§7), and becomes a source of CI flakiness once it starts failing on
infrastructure noise rather than real regressions. This is a deliberate
omission, not an oversight.
